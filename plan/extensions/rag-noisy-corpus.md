# RAG: шумный корпус и семантические коллизии — стратегии исправления

Методический документ: как правильно чинить retrieval, когда RAG возвращает шум или
«не знаю» несмотря на корректный индекс. Возник из диагностики дня 31 (fix multilingual),
но применим к любому RAG-домену. Слоистая стратегия — от дешёвого и точного к дорогому.

Связанные файлы проекта:
- `src/main/kotlin/com/cliagent/rag/RagRetriever.kt` — pipeline rewrite→embed→topK→rerank
- `src/main/kotlin/com/cliagent/rag/rewrite/*QueryRewriter.kt` — слой 2 (query rewrite)
- `src/main/kotlin/com/cliagent/rag/rerank/*Reranker.kt` — слой 3 (реранкинг)
- `src/main/kotlin/com/cliagent/rag/DocumentLoader.kt` — слой 0 (состав корпуса)
- `src/main/kotlin/com/cliagent/rag/chunk/*Chunker.kt` — слой 1 (chunking)
- `src/main/kotlin/com/cliagent/rag/RagModels.kt:RagConfig` — конфиг (corpusRoots, topK, candidatePoolSize)
- `src/main/kotlin/com/cliagent/cli/RagCommands.kt` — `/rag eval`, `/rag compare` (метрики)

---

## 0. Сначала — диагностика типа шума

«Шумный корпус» — зонтичный термин. Прежде чем чинить, определи тип проблемы,
потому что решения разные (иногда противоположные):

| Тип | Симптом | Пример из проекта |
|-----|---------|-------------------|
| **A. Мусорные источники** | Чанки из нерелевантных файлов доминируют | `plan/` (2489 чанков) топил `AGENTS.md` (18 чанков) в дне 31 |
| **B. Семантическая коллизия** | Похожие понятия в разных контекстах; retrieval путает | «strategy» = context-strategy ИЛИ reasoning-strategy |
| **C. Языковой барьер** | Запрос и корпус на разных языках | русский «технический стек» vs английский `Tech Stack` |
| **D. Форматный барьер** | Структурированные данные (таблицы/код) плохо embedding-матчатся | таблица Tech Stack vs естественный текст запроса |
| **E. Масштаб** | Миллион чанков, top-K тонет в шуме | крупная кодовая база (>10K файлов) |

**Главное правило:** чинить начиная с самого дешёвого и точного слоя, не прыгая сразу
в ML-тюнинг. 90% проблем решается слоями 0-2.

---

## 1. Слоистая стратегия (от дешёвого к дорогому)

```
Слой 0: Состав корпуса        ← дёшево, наибольший эффект (тип A)
Слой 1: Chunking              ← структура данных (типы B, D)
Слой 2: Retrieval pipeline    ← rewrite + candidate pool (типы B, C)
Слой 3: Реранкинг             ← дорогой, но точный (типы B, E)
Слой 4: Тюнинг embedding-модели ← последнее средство (типы C, D)
```

### Слой 0 — состав корпуса

**Применимо к:** тип A (мусорные источники). Самый высокий ROI: один чанк мусора в индексе
хуже, чем 10 в retrieval — потому что он «отбирает» слот у релевантного чанка в top-K.

**Корректный подход:**
- **Whitelist источников** — явно перечислить, что индексируем (не «всё что найдётся»).
  В проекте: `RagConfig.corpusRoots = [README.md, AGENTS.md, src/main/kotlin]` вместо
  дефолта с `plan/`. Сужение с 2973 → 484 чанков в дне 31.
- **Чёрные списки паттернов** — skip `build/`, `node_modules/`, `.gradle/`, `target/`.
  Уже реализовано в `DocumentLoader.SKIP_DIRS`.
- **Ранжирование источников по авторитету** — если `README.md` и `plan/notes.md` описывают
  «стек», README «авторитетнее». Метаданные чанка могут хранить вес источника.

**Антипаттерн:** добавлять ещё больше источников «на всякий случай». Чем больше шума,
тем хуже top-K работает при фиксированном K.

### Слой 1 — chunking (как режем)

**Применимо к:** типы B, D. Структура чанка определяет, насколько хорошо он матчится.

**Подводные камни:**
- **FixedSizeChunker** режет таблицу Tech Stack посередине → чанк содержит половину
  таблицы, embedding получается бессмысленный. Плохо для типа D.
- **StructuralChunker** (default в проекте) режет по заголовкам `##` → таблица попадает
  в чанк целиком. Лучше, но таблица всё ещё «неестественный» текст для embedding-модели.

**Корректные техники:**
- **Синтетическое описание для structured-чанков** — после таблицы добавить текстовое
  summary: `«Tech Stack включает Kotlin, Gradle, clikt, JLine3, Ktor, MCP SDK...»`.
  Даёт embedding-модели естественный текст, который матчится с запросом.
- **Markdown-aware chunking** — таблицы преобразовать в CSV/DDL-подобный плоский текст
  перед embedding (но показывать оригинал пользователю).
- **Metadata enrichment** — чанк хранит `{source, section, parent_section}`, и retrieval
  может фильтровать/бустить по секции (например, только `## Tech Stack`).

### Слой 2 — retrieval pipeline (rewrite + candidate pool)

**Применимо к:** типы B, C. Здесь живёт фикс дня 31.

**Корректные техники (по возрастанию сложности):**

1. **Query rewrite** — переформулировать запрос перед embedding. В проекте:
   - `HeuristicQueryRewriter` — удаляет стоп-слова, нормализует (дёшево, deterministic)
   - `LlmQueryRewriter` — синонимы, расширение аббревиатур, **сохранение языка** (неделя 5)
   - `DevAssistantQueryRewriter` (день 31 fix) — перевод на язык корпуса + технические
     синонимы. Правильный ответ на тип C.

2. **Candidate pool + двухэтапный retrieval** — вместо «top-5 сразу», сначала `top-20`
   (широкий recall), потом сузить. В проекте: `RagRetriever` с `candidatePoolSize=20` +
   reranker. Широкий pool даёт шанс релевантному чанку, который при `top-5` выпал бы на
   6-й позиции из-за шумного соседа.

3. **Hybrid search** — combine dense (embedding) + sparse (BM25/keyword). Embedding хорош
   на семантике, но плох на точных терминах («GLM-5.1», «clikt 4.4.0»). Гибрид покрывает
   оба. В проекте НЕТ — Phase 2.

### Слой 3 — реранкинг (пересортировка после retrieval)

**Применимо к:** типы B, E. Самый мощный инструмент для «похожие понятия в разных контекстах».

В проекте три reranker'а (неделя 5):
- **ThresholdReranker** — отсекает по порогу similarity (защита от нерелевантного). Дёшево.
- **HeuristicReranker** — keyword overlap, позиция термина. Быстро.
- **LlmReranker** — LLM оценивает релевантность каждого чанка запросу (0-10). Дорого
  (~N LLM-вызовов на pool), но самое точное.

**Корректный паттерн для шумного корпуса:**
`candidatePoolSize=20` (широкий recall) → `LlmReranker` (точная фильтрация) → `top-5`.
Reranker «видит» чанк целиком и запрос, может отличить «strategy = context-strategy» от
«strategy = reasoning-strategy» по контексту, который embedding-модель не различает.

**Когда НЕ применять реранкинг:** если pool маленький (5-10 чанков) и шум слабый —
накладные расходы LLM-вызовов не окупаются. Сначала слои 0-2.

**Включение в проекте:** `config.rag.reranker = "llm"` + `config.rag.candidatePoolSize = 20`.

### Слой 4 — тюнинг embedding-модели (последнее средство)

**Применимо к:** типы C, D, когда дёшевые слои исчерпаны.

- **Сменить embedding-модель на мультиязычную** — `multilingual-e5-large`, `bge-m3`
  поддерживают русский+английский в одном пространстве. Минус: больше RAM (~2GB), дольше
  embedding. В проекте: `config.rag.embeddingModel`.
- **Fine-tune под домен** — если корпус специфичный (медицина, юр), общая модель матчит
  плохо. Дорого, требует labeled pairs.
- **Domain-adapted prompts для embedding** — некоторые модели (E5, BGE) поддерживают
  префиксы: `"query: ..."` / `"passage: ..."`. У `nomic-embed-text` этого нет.

## 2. Антипаттерны (что НЕ надо делать)

1. **Поднимать `topK` «чтобы точно попало»** — при шумном корпусе просто больше мусора в
   ответе, контекстное окно забивается, LLM теряется. Лучше сузить corpus / добавить
   reranker, чем раздувать K.

2. **«Переведём весь корпус на английский»** — workaround для типа C, но ломает source
   citation (агент будет цитировать перевод, не оригинал). Правильно — переводить
   **запрос** (как в `DevAssistantQueryRewriter`), корпус остаётся как есть.

3. **Игнорировать chunk boundaries** — резать fixed-size по 1000 токенов «чтобы больше
   влезло». Теряется семантическая цельность чанка, retrieval ухудшается. Structural >
   Fixed для документации.

4. **Прыгать в ML-тюнинг без слоёв 0-2** — самая частая ошибка. 90% проблем RAG-качества
   решаются составом корпуса + chunking + query rewrite. Fine-tune embedding-модели имеет
   смысл только когда первые три слоя выжаты.

5. **Доверять cosine similarity без калибровки** — «0.7 = релевантно» миф. Порог зависит
   от модели, домена, длины чанка. `ThresholdReranker` с фиксированным 0.3 может как
   отсечь хорошее, так и пропустить плохое. Нужен baseline на эталонных запросах.

## 3. Метрики — как понять, что починилось

Без метрик чинишь «на глаз», и регрессии незаметны. Минимальный набор:

1. **Golden set** — 20-50 эталонных запросов с ожидаемым источником (для «tech stack» →
   должен быть `AGENTS.md › Tech Stack`). Прогоняешь до/после фикса, считаешь `hit@k`
   (нашёлся ли ожидаемый чанк в top-K).
2. **Recall@K** — доля запросов, где релевантный чанк попал в top-K. Растёт → фикс помогает.
3. **MRR (Mean Reciprocal Rank)** — средняя позиция релевантного чанка. Должна расти
   (1.0 = всегда топ-1).
4. **LLM-graded relevance** — для субъективных запросов: LLM оценивает ответ 1-10. Дорого,
   но для production.

В проекте: `/rag eval` и `LocalRagCompare` — ровно тот инструмент. Перед любым фиксом RAG —
замеряешь baseline, после — сравниваешь.

## 5. Подводные камни thinking-моделей (отдельно от RAG)

Найдено при диагностике дня 31, не относится к слоям RAG, но критично для любого
LLM-вызова в pipeline (query rewrite, rerank, generation):

**Симптом:** GLM-5.1, qwen3 (thinking-модели) на русских промптах при `maxTokens=256`
отдавали `completionTokens=256` с **ПУСТЫМ** `content` — вся квота уходила на внутренний
reasoning, до ответа дело не доходило.

**Фикс:** поднять `maxTokens` до 1024+ в rewriter'ах/reranker'ах — reasoning успевает
завершиться и выдать content. `DevAssistantQueryRewriter` использует 1024.

**Где проверять:** любой LLM-вызов с малым `maxTokens` (< 512) на thinking-модели —
кандидат на пустой content. Особенно когда запрос «сложный» для модели (перевод,
многоязычность, абстрактные инструкции).

## 6. Алгоритм принятия решения

```
1. Замерить baseline (hit@5 на golden set через /rag eval)
2. Тип шума?
   A (мусор)         → слой 0 (состав корпуса)       [1 час, огромный эффект]
   C (язык)          → слой 2 (query rewrite/перевод) [сделано в дне 31]
   B (коллизия)      → слой 3 (LlmReranker)           [есть в проекте]
   D (формат)        → слой 1 (synthetic summaries)   [доработка chunker'а]
   E (масштаб)       → слои 2+3+hybrid search         [Phase 2]
3. Замерить после → hit@5 вырос? → стоп
4. Если нет → следующий слой
5. Fine-tune embedding-модели — последним, когда всё остальное выжато
```

Главное — не «чуешь ли, что стало лучше», а **метрика до/после**. Без неё любой фикс — гадание.
