## Контекст лекции недели 5 (RAG)

**RAG (Retrieval Augmented Generation)** — паттерн дополнения ответов LLM внутренними знаниями
**во время инференса** (в отличие от MCP = внешние источники, fine-tuning = изменение весов).

Пайплайн с RAG (лекция):
1. Пользователь задаёт вопрос
2. Модель анализирует запрос → ищет пробелы в знаниях
3. Запрос обращается к векторной базе документов
4. Находятся семантически похожие чанки
5. **Чанки комбинируются с промптом**
6. Модель возвращает ответ со ссылкой на источник

Шаг 5 — именно то, что реализует день 22: инъекция retrieved-чанков в промпт.

Ключевые понятия из лекции, применённые в день 22:
- **Косинусное сходство** (1=идентичны, 0=ортогональны) — `VectorMath.cosine`/`topK` (день 21).
- **Чанки + эмбеддинги** — индекс корпуса проекта (день 21).
- **Анти-галлюцинации** — модель отвечает из чанков, а не из «общей памяти». Метаданные source/section
  кладутся в промпт явно → задел под день 24 (обязательные цитаты).
- **Мягкая деградация** — RAG опционален; без Ollama/индекса агент не падает.

## Маппинг задания → реализация

| Требование задания | Реализация |
|---|---|
| вопрос → поиск чанков → объединение с вопросом → запрос к LLM | `RagRetriever.retrieve()` + инъекция в `PromptBuilder` + `ContextAwareAgent.chat()` |
| ответ без RAG | `/rag off` (или `RagConfig.enabled=false`) → `ragContext=null` → базовый промпт |
| ответ с RAG | `/rag on` → retrieval каждого хода → блок `[Retrieved context]` в system-prompt |
| 10 контрольных вопросов | `resources/rag/eval-questions.json` (id, question, expectedKeywords, expectedSources) |
| зафиксировать ожидание | `expectedKeywords` — ключевые слова, которые должны быть в ответе |
| зафиксировать источники | `expectedSources` — файлы, из которых должен прийти контекст |
| сравнение качества | `/rag eval` — прогон обоих режимов, отчёт по покрытию keywords (Δ RAG vs no-RAG) |
| агент с двумя режимами | `ContextAwareAgent` + runtime toggle `ragEnabled` (`setRagEnabled/isRagEnabled`) |

## Решения и обоснования

### 1. `RagRetriever` — отдельный класс, не метод в `RagCommands`

До дня 22 паттерн `load → embed(query) → topK` дублировался в `RagCommands.handleSearch` и
`ChunkingComparison.probe`. Вынесение в `RagRetriever` (DRY) позволяет: агенту и CLI использовать
один retrieval-путь; тестировать изолированно (mock `EmbeddingClient` + `@TempDir`); переиспользовать
в `/rag eval`. `retrieve()` возвращает `null` при ошибке/пустом индексе → мягкая деградация без throw.

### 2. Инъекция через `PromptBuilder`, а не отдельное сообщение

`PromptBuilder` уже компонует слоёный system-prompt. Добавление `retrievedContext`-параметра (default
`null` → байт-идентично дням 11–21) сохраняет единый seam и ordering: base → long-term → working →
**retrieved** → invariants. Альтернатива (отдельное system-сообщение с чанками) ломала бы существующий
`buildMessagesToSend` и контракт context-strategies.

### 3. `Agent.chat()` сигнатура не меняется

RAG-контекст собирается внутри реализации (агент сам retrieve'ит по `userMessage`), а не через
параметры. Каждый ход → свежий retrieval (лекция: инференс-тайм). Это сохраняет интерфейс `Agent`
стабильным и не требует править `StatefulAgent`/`TaskOrchestrator`/все call-site'ы.

### 4. Runtime toggle `/rag on|off` + `/rag eval`

Дефолт режима — `RagConfig.enabled` (статический config). Runtime-toggle позволяет A/B-сравнение в
одном чате без перезапуска (требование задания «два режима + сравнение»). `/rag eval` автоматизирует
прогон 10 вопросов: для каждого — ответ без RAG и с RAG, отчёт по покрытию expectedKeywords (Δ).
